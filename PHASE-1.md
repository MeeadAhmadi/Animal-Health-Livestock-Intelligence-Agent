# Phase 1 — Backend + PostgreSQL Foundation

## Goal

Build the first real backend foundation for the Livestock Intelligence & Early-Warning System by introducing a reliable PostgreSQL-backed application core.

Phase 1 converts the Phase 0 project skeleton into a backend foundation that is ready for later source collection, normalization, intelligence logic, authentication, dashboard development, and AI/RAG work.

Phase 1 is intentionally focused on **backend infrastructure** rather than product features.

At the end of Phase 1, the project should have:

- centralized backend configuration

## Included Scope

### 1. Backend Configuration

Implement centralized settings management for the backend.

Requirements:

- environment-based configuration
- validation of required settings
- development-safe defaults where appropriate
- PostgreSQL connection settings
- no hardcoded credentials
- no real secrets committed to Git
- configuration structure that can evolve into later production use

Expected outcome:

- backend configuration is no longer scattered or implicit
- database connectivity can be controlled via environment variables
- invalid configuration fails clearly and safely

### 2. PostgreSQL

Introduce PostgreSQL as the primary relational database.

Requirements:

- local PostgreSQL development instance
- application-level database connection
- explicit database lifecycle handling
- database availability checks
- application must not permanently run using the PostgreSQL superuser
- separate database/app user strategy for the application
- local-only development topology is acceptable

Development note:

If native Windows installation remains unavailable or blocked, PostgreSQL may run in WSL/Linux during development while FastAPI continues to run on Windows.

This is acceptable for development.

### 3. SQLAlchemy 2.x

Introduce SQLAlchemy as the database access layer.

Requirements:

- SQLAlchemy 2.x usage
- engine creation
- session factory
- dependency injection support for DB sessions
- declarative base setup
- clean separation between database infrastructure and API logic
- safe parameterized query mechanisms through SQLAlchemy
- no unsafe raw SQL concatenation with user-controlled values

Important rule:

Phase 1 must **not** invent speculative intelligence-domain tables just because they may be useful later.

### 4. Psycopg 3

Use Psycopg 3 as the PostgreSQL driver for SQLAlchemy/PostgreSQL integration.

Requirements:

- dependency added and documented
- compatible connection configuration
- tested database connectivity

### 5. Alembic

Alembic is the approved migration system.

Requirements:

- Alembic initialized and configured
- migration history committed to Git
- migration workflow documented
- database credentials must not be stored directly in committed Alembic config
- autogenerated migrations must be reviewed before applying
- destructive migrations require explicit review
- application startup must not silently apply uncontrolled schema changes
- `Base.metadata.create_all()` must not replace the migration workflow

Purpose:

Alembic ensures schema evolution remains traceable, reviewable, and reproducible.

### 6. Database Infrastructure Only

Phase 1 introduces **infrastructure**, not the final domain schema.

That means Phase 1 may create the minimum schema needed to prove the DB/migration workflow works, but it must **not** prematurely design the entire intelligence database.

Examples of future domain areas that are **not** automatically part of Phase 1:

- sources
- evidence
- events
- signals
- trends
- funding opportunities
- company context
- user accounts
- sessions
- audit logs

These must be introduced only when their requirements and downstream consumers are clearly defined.

### 7. Health vs Readiness

The backend must distinguish between:

- **liveness**: the API process is running
- **readiness**: required dependencies are available

Requirements:

- `/health` remains the liveness endpoint
- a readiness check must validate the database dependency
- the API must not claim full readiness if PostgreSQL is unavailable

This separation is important because a running API process is not equivalent to an operational backend.

### 8. Error Handling

Introduce a centralized backend error-handling foundation.

Requirements:

- consistent backend exception handling
- internal stack traces must not be exposed to normal clients
- database credentials must never leak in API errors
- predictable responses for operational failures where applicable
- internal errors should still be logged with useful diagnostic context

This is a foundational phase, so the goal is correctness and safety, not yet a perfect end-user error UX.

### 9. Structured Logging

Introduce structured application logging.

Requirements:

- UTC timestamps
- log levels
- structured log format
- request ID / correlation ID support
- consistent exception logging
- clear separation between operational logs and future security audit logs

Logs must never intentionally contain:

- passwords
- database passwords
- tokens
- session identifiers
- API keys
- secret values
- authorization headers
- sensitive raw request bodies

### 10. Observability Foundation

Phase 1 does not deploy the full observability stack, but it must prepare the backend for it.

Phase 1 foundation should support later integration with:

- Prometheus
- Loki
- Grafana
- OpenTelemetry

Included in Phase 1:

- request/correlation ID foundation
- request timing foundation
- exception instrumentation foundation
- database health visibility
- code structure that will not need redesign later to add telemetry

Not included in Phase 1:

- full Prometheus deployment
- full Grafana dashboards
- full Loki deployment
- full distributed tracing backend

### 11. Security Direction for Phase 1

Phase 1 security goals:

- no secrets committed
- no real `.env` committed
- no app use of permanent PostgreSQL superuser credentials
- safe database access patterns
- controlled error exposure
- log redaction discipline
- local CORS remains development-only
- external content handling is deferred because collection is not yet implemented

Important note:

Authentication is **not** part of Phase 1 under the standalone-web roadmap.

### 12. Local Development Only

Phase 1 is still local-first.

Approved development model:

- PostgreSQL local
- frontend local
- no production deployment
- no paid hosting required

The purpose is to prove the architecture works before introducing operational complexity.

## Known Risks in Phase 1

### 1. Wrong database privilege model
Impact: 8/10

If the application is run permanently with PostgreSQL superuser credentials, the blast radius of a future backend vulnerability becomes too large.

### 2. Poor migration discipline
Impact: 8/10

If schema changes happen ad hoc without Alembic discipline, later development becomes fragile and unsafe.

### 3. False health reporting
Impact: 7/10

If the API reports healthy while PostgreSQL is unavailable, operational debugging becomes misleading.

### 4. Secret leakage in logs/errors
Impact: 8/10

If configuration or errors leak credentials, the public repository and future environments become risky.

### 5. Premature schema design
Impact: 6/10

If we invent too many domain tables too early, we lock ourselves into weak assumptions before the collection and intelligence phases clarify requirements.

### 6. WSL-based PostgreSQL complexity in development
Impact: 3/10

This is acceptable and manageable if Windows-native installation is blocked.

## 3. Architecture Decisions

### PostgreSQL as the relational database

PostgreSQL is now the primary relational database foundation.

The current development topology is:

- FastAPI running locally on Windows
- PostgreSQL running locally through WSL
- frontend running locally
- no production infrastructure

This topology is approved for local Phase 1 development.

### Runtime and migration roles are separated

The backend application does not run with PostgreSQL superuser credentials.

Confirmed roles:

- `li_app` — runtime application role
- `li_migrate` — migration login role
- `li_owner` — non-login ownership role

The runtime application connects as `li_app`.

Alembic connects as `li_migrate` and explicitly activates `li_owner` for schema migration operations.

This reduces the privilege available to the normal FastAPI runtime.

### Application schema

The application schema is:

`app`

The SQLAlchemy declarative metadata is scoped to this schema.

No speculative intelligence-domain tables were created during Phase 1.

### Migration discipline

Alembic is the exclusive schema-migration foundation.

Application startup does not automatically apply schema migrations.

`Base.metadata.create_all()` is not used as a replacement for Alembic.

Migration revisions must remain explicit, reviewable, and committed to version control.

### Liveness and readiness are separate

`/health` confirms that the API process is alive.

`/ready` verifies PostgreSQL availability using an actual database query.

A running API process therefore does not automatically imply backend readiness.

### Request correlation

Every inbound request receives a backend-generated UUID request ID.

The request ID is:

- stored in request state
- stored in request-local context for logging
- returned through `X-Request-ID`
- included in structured request logs
- included in controlled HTTP 500 responses
- included in exception logs

Inbound user-provided request IDs are not trusted during Phase 1.

### Structured logging

Application logs use JSON and UTC timestamps.

Current structured fields include:

- timestamp
- level
- logger
- message
- request ID where available

Request completion logging also records:

- HTTP method
- request path
- response status
- processing duration

Sensitive request bodies, authorization headers, passwords, API keys, tokens, and database credentials are not intentionally logged.

### Centralized errors

Unhandled application exceptions are converted into generic HTTP 500 responses.

Internal exception details and stack traces are not returned to normal clients.

The client receives a request ID that can be correlated with internal logs.
